## 0. Preliminary Phase

### 0.1 Initial Thoughts: Research Before Building

My first instinct was to research before writing any code. I watched videos on the Claude Agent SDK, read through the documentation, and gathered context on best practices. I learned about validators, hooks, tools, and sub-agents — the building blocks the SDK provides for complex agent workflows.

I found myself thinking about scaling and architecture before I'd even touched the codebase. How would agents communicate? What would the orchestration look like? Where would state live? These felt like important questions to answer upfront.

### 0.2 First MVP: Model Too Good

Then I built the first MVP — and everything I'd planned for became irrelevant.

I built without foundations: no schema file, minimal system prompts, just the raw CSV data and a basic agent. The surprise? Haiku handled most queries correctly out of the box. Data analysis with pandas turned out to be too easy for modern LLMs. The model didn't need my carefully planned validators or hooks — it just... worked.

This created an unexpected problem: nothing to improve if there are no errors.

### 0.3 Limitations and Dilemmas

I hit walls from multiple directions simultaneously:

- **Defining success** — What does "better" mean when the model is already correct?
- **Task too easy** — Pandas queries over structured data is well within LLM capabilities
- **Architecture complexity** — My planned orchestrator felt like overkill for what the task actually needed
- **Time constraints** — Limited runway to iterate on approaches
- **First time using Agent SDK** — Learning curve on top of everything else

The core insight was counter-intuitive: I had to *undo* best practices. Validators and hooks would have helped the agent succeed on the first try — but I needed it to struggle so there was something to improve. The features that would make a production system robust were working against my goal of demonstrating learning.

### 0.4 Trade-offs Forced Early

This led to deliberate handicapping:

- Remove helpful context to force struggles
- Use weaker model (Haiku) intentionally instead of Opus
- Abandon SDK features that would help too much
- Strip out schema information the agent could have used

I was engineering difficulty into a system that wanted to succeed.

## 1. Establishing Baseline Performance

### 1.1 Blind Test — Benching Claude

I tested through an interactive shell, running queries one-by-one and observing behavior in real-time. No schema, no system prompt, just the raw data file. This gave me direct visibility into how the model reasoned and where it stumbled.

The observation was consistent: surprisingly capable even with no guidance. Haiku could figure out column names, understand data relationships, and write correct pandas code without any help. The "blind" agent was hardly blind at all.

### 1.2 Haiku 4.5 — Probing for Weakness

Finding queries that actually challenged the model required combinations of:

- **Deeply nested** — Multi-step aggregations and joins
- **Ambiguous** — Questions with multiple valid interpretations
- **Domain knowledge** — Requiring understanding of financial concepts
- **Edge cases** — Boundary conditions and unusual data patterns

No single pattern caused struggles. I could throw complex aggregations at it and Haiku would handle them fine. I had to be truly adversarial — combining multiple difficulty factors in a single query — to find weaknesses worth exploiting.

### 1.3 Golden Suite, MVP & Next Steps

To systematically find struggle patterns, I spawned 50 Opus sub-agents across a broad range of queries. The key was combining signals:

- **Tokens consumed** — More tokens suggested more reasoning/backtracking
- **Tool calls made** — More calls meant more iteration
- **Backtracking patterns** — Revising approach mid-stream

I selected 9 training queries and 8 test queries that maximized these signals — the ones where even capable models had to work for the answer. Gold-standard answers were generated by Opus 4.5 with extended thinking enabled, giving me ground truth without solving everything by hand.

### 1.4 Success Pivot

Correctness saturated quickly. Haiku got answers right even on hard queries — it just took more work to get there.

This forced a pivot in success metrics. Instead of measuring accuracy, I measured efficiency:

- **Tokens consumed** — Same answer, fewer tokens = improvement
- **Tool calls** — Same answer, fewer iterations = improvement

The new goal: achieve the same correct answer with fewer resources. The system would learn to take shortcuts, avoid dead ends, and apply patterns from previous queries.

## 2. Minimal Viable Improver

### 2.1 The First MVP — Evaluator Chain

My initial design was a clean three-stage pipeline:

```
Learner → Evaluator → Improver
```

Separation of concerns: the Learner answers queries, the Evaluator judges quality, the Improver updates knowledge. Each agent had a focused responsibility. An orchestrator coordinated the handoffs.

This was architecturally satisfying. It was also too slow.

### 2.2 Collapse to Learner + Improver

Multiple pressures combined to collapse the pipeline:

- **Latency** — Waiting 50+ seconds between queries in an interactive shell was painful. The orchestrator added overhead for a workflow that was otherwise straightforward.
- **Diminishing returns** — The Evaluator's judgment often duplicated what the Improver figured out anyway. Opus could handle both evaluation and improvement in a single pass.
- **Time pressure** — Less time to iterate meant simpler architecture wins.

What emerged:

- **Evaluator merged into Improver** — Opus 4.5 could judge quality and apply fixes in one step
- **Self-reflection added to Learner** — Sometimes the agent's own reflection caught nuances an external judge missed
- **Async background improver** — Improvements run in a background thread, unblocking the interactive shell

The Learner now writes reflections to disk. The Improver picks them up asynchronously, evaluates, and updates knowledge files. No orchestrator needed.

### 2.3 What Got Cut

- **Orchestrator** — Unnecessary complexity for a two-agent workflow
- **Separate Evaluator** — Opus Improver absorbed this responsibility
- **Batching** — The N+1 requirement demanded per-query updates, not learning after 50 examples
- **Validators/hooks** — Would have helped the agent succeed too easily

The final architecture is minimal: Learner (Haiku) answers queries and reflects, Improver (Opus) judges and updates knowledge files. Everything else was cut.

---

*The journey from over-engineered vision to working prototype required letting go of best practices that didn't serve the goal. Sometimes the right architecture is the simplest one that demonstrates the concept.*
